## Feature: CPU Target-Tracking Autoscaling Policy

Added `aws_autoscaling_policy` to the Clixx ASG (mirroring the same change made to Blog):

```hcl
resource "aws_autoscaling_policy" "cpu_target_tracking" {
  name                   = "cpu-target-policy"
  autoscaling_group_name = aws_autoscaling_group.tf-asg.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 80.0
  }
}
```

AWS will now automatically scale the Clixx fleet up/down to maintain ~80% average CPU. No separate CloudWatch alarms required — TargetTrackingScaling manages them internally.

## Fix: git clone Branch Flag

The `git clone` command had a subtle syntax bug — `--branch` was placed after the URL but before the target directory, and the branch name was missing:

```bash
# Before (broken — no branch name provided)
git clone https://github.com/stackitgit/CliXX_Retail_Repository.git
cp -r CliXX_Retail_Repository/* ${EFS_MOUNT_POINT}/
rm -rf /var/www/html/CliXX_Retail_Repository

# After (clones the 'latest' branch directly into the mount point)
git clone --branch latest ${GIT_REPO}
cp -r CliXX_Retail_Repository/* ${EFS_MOUNT_POINT}/
rm -rf ${EFS_MOUNT_POINT}/CliXX_Retail_Repository
```

Also: the hardcoded GitHub URL was replaced with a `GIT_REPO` variable set in `local_env()`:
```bash
GIT_REPO="https://github.com/stackitgit/CliXX_Retail_Repository.git"
```

And the `rm -rf` path was fixed — it was pointing at `/var/www/html/CliXX_Retail_Repository` (absolute path) when it should be relative to `${EFS_MOUNT_POINT}`.

## Fix: WP-CLI URL Sync in Addition to SQL

The `siteurl`/`home` update was originally done only via raw SQL:

```sql
UPDATE wp_options SET option_value = '${SITE_ADDR}' WHERE option_name = 'siteurl';
UPDATE wp_options SET option_value = '${SITE_ADDR}' WHERE option_name = 'home';
```

This updated the database but didn't always flush WordPress's object cache, which meant the old URL could still appear in cached responses for a period after deployment.

Added `wp option update` calls alongside the SQL:

```bash
wp option update siteurl "${SITE_ADDR}" --allow-root
wp option update home "${SITE_ADDR}" --allow-root
```

WP-CLI flushes the relevant caches when it updates options, ensuring the new URL takes effect immediately.
