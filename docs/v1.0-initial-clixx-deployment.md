## What Was Built

Full infrastructure-as-code for the Clixx Retail WordPress application. Clixx is a separate app from the Blog — it has its own EC2 instance, RDS database (restored from a snapshot of existing Clixx data), EFS mount, and user-data bootstrap.

This PR also renamed `stack-Instance` → `stack-Blog` to better reflect each stack's actual workload.

---

## How Clixx Differs from stack-Blog

| | stack-Blog | stack-Clixx |
|---|---|---|
| Compute | Auto Scaling Group (1–3 instances) | Single EC2 instance |
| Database | Provisioned from snapshot of `wordpressinstance` | Restored from `clixx-working-snapshot` |
| URL reconciliation | Raw SQL + `mysql` CLI | WP-CLI (`wp option update`) |
| Plugin management | WP-CLI | WP-CLI |
| Directory structure | `user-data/user-data.sh` | `scripts/user-data.sh` |

## user-data Bootstrap Sequence

1. **Pull config from SSM** — all credentials and config stored under `/stack/clixx/*`
2. **Install system packages** — `httpd`, `php`, `mariadb` client, `lvm2`, `nfs-utils`, `git`
3. **Mount EFS** at `/var/www/html` (same nfs4 pattern as Blog)
4. **Partition and mount EBS volumes via LVM** — same `stack_vg` pattern, mounts at `/u01`…`/u0N`
5. **Configure Apache + PHP** — set permissions, enable `.htaccess`
6. **Clone Clixx repo** — `https://github.com/stackitgit/CliXX_Retail_Repository.git` to EFS; skip if already present
7. **Generate wp-config.php** from SSM values
8. **Start services** — `httpd`, `mariadb`, `php-fpm`
9. **Install WP-CLI** if not present
10. **Update `siteurl`/`home`** via raw SQL + `wp option update`
11. **Install and activate `wp-force-login`** plugin (login page required from day one, unlike Blog where it was added in v1.2)

### Why WP-CLI for URL Updates

The Blog originally used raw `mysql` commands to update `siteurl`/`home`. Clixx used `wp option update` from the start, which is safer — it goes through WordPress's own data layer and flushes caches properly, whereas direct SQL can leave stale cached values in WordPress's object cache.

## RDS: Restore from Snapshot

```hcl
data "aws_db_snapshot" "latest_prod_snapshot" {
  db_snapshot_identifier = "clixx-working-snapshot"
  most_recent            = true
}

resource "aws_db_instance" "clixx" {
  snapshot_identifier = data.aws_db_snapshot.latest_prod_snapshot.id
  ...
}
```

Using a `data` source (instead of `resource "aws_db_snapshot"` as in Blog) to reference a snapshot that already exists in AWS rather than creating a new one. `most_recent = true` means if multiple snapshots match the identifier, the newest is used.
