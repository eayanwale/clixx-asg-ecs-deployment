## Feature: Seed Contributor Users

### Goal

Automatically create three pre-defined contributor-role WordPress accounts on first deploy so reviewers have accounts ready without needing a manual `wp user create` after each fresh environment.

### Implementation

Added a loop in `scripts/user-data.sh` after the `wp-force-login` plugin install:

```bash
default_users=(
    "mike user1@example.com --role=contributor"
    "chichi user3@example.com --role=contributor"
    "pete user4@example.com --role=contributor"
)

for user in "${default_users[@]}"; do
    IFS=' ' read -r user_login user_email _ <<< "${user}"

    if wp user get "${user_login}" --allow-root >/dev/null 2>&1; then
        echo "User ${user_login} already exists, skipping"
    else
        wp user create "${user_login}" "${user_email}" --role=contributor --send-email --allow-root
    fi
done
```

**Idempotent:** `wp user get` check before each `wp user create` — re-running on a pre-populated EFS mount won't create duplicate users or send duplicate welcome emails.

**`--send-email`:** WordPress sends a welcome email with a password reset link to each new user. Since we're not setting a password in the command, this is how the user gets access to their account.

## Issue: ALB Health Check Failing with 301

### What Happened

After deploying Clixx with `wp-force-login` active, the ALB health check was intermittently marking instances unhealthy. The initial fix set `matcher = "200,302"` (covering the standard login redirect), but some request paths were returning `301 Moved Permanently` instead of `302 Found`.

This appears to happen when WordPress returns a canonical redirect (e.g. for trailing-slash enforcement or `www` → non-www normalization) before it even gets to the login redirect.

### Fix

Updated `matcher` in the `health_check` block of `aws_lb_target_group` in `ec2.tf`:

```hcl
# Before
matcher = "200,302"

# After
matcher = "200,301,302"
```

Now the ALB accepts `200`, `301`, and `302` as healthy responses, covering all expected redirect patterns from a fresh WordPress install with forced login.

## Note on Health Check Status Codes

The progression across stacks:
1. **Blog v1.0** — default health check, only `200` accepted (no explicit matcher)
2. **Blog v1.2** — added `matcher = "200,302"` after `wp-force-login` caused `302` to fail health checks
3. **Clixx v1.0** — launched with `matcher = "200,302"` from the start
4. **Clixx v1.2 (this)** — expanded to `matcher = "200,301,302"` after 301 redirects surfaced
